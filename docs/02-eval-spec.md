## 1. 用例 schema

```json
{
  "case_id": "IMP-0019",
  "title": "发票总价与报关单差 120 美元",
  "tags": ["不一致", "金额"],
  "noise": [],
  "docs": {
    "contract":   { "...": "..." },
    "invoice":    { "...": "..." },
    "packing_list": { "...": "..." },
    "bl":         { "...": "..." },
    "declaration":{ "...": "..." }
  },
  "injected_defects": ["L2-13"],
  "expected": {
    "verdict": "FIX",
    "issues": [
      {"rule_id": "L2-13", "field_path": "declaration.total_amount", "severity": "high"}
    ],
    "citations": ["内审SOP 3.2 金额勾稽"],
    "must_not": ["L2-12"]
  },
  "scoring": {"verdict": 0.4, "issue_recall": 0.4, "citation": 0.2}
}
```

**`must_not` 是重点**：用来测误报。明明没问题的字段被报出来，就要扣分。

|---|---|---|---|

## 3. 三个代表性样例

### ① IMP-0007 → PASS（防误报）

四单品名、数量、币制一致；毛重 1,200.5 kg vs 1,215.0 kg，差 1.2%，在 ±3% 容差内。
发票 48,000 USD = 单价 12 × 数量 4,000，勾稽正确。

```json
"expected": {"verdict": "PASS", "issues": [], "must_not": ["L2-15", "L1-07"]}
```

**考点**：抓“为了显得有用而乱报警”的 Agent。

### ② IMP-0019 → FIX（差异定位）

发票总额 48,000 USD，报关单 47,880 USD，差 0.25%；数量一致。

```json
"injected_defects": ["L2-13"],
"expected": {
  "verdict": "FIX",
  "issues": [{"rule_id": "L2-13", "field_path": "declaration.total_amount", "severity": "high"}],
  "citations": ["内审SOP 3.2"],
  "must_not": ["L2-12"]
}
```

**考点**：能不能定位到**具体字段**，而不是笼统说“金额有问题”。总额差 0.25% 已超过 0.1% 的总额容差
（行级勾稽用 1%，总额用 0.1%，两者不同）。

### ③ IMP-0041 → REVIEW（不敢下结论）

品名“塑料制玩具配件”，申报 9503.00；箱单写“PVC 管件”，提单写“PLASTIC FITTINGS”。

```json
"expected": {
  "verdict": "REVIEW",
  "issues": [{"rule_id": "L3-25", "field_path": "declaration.items[0].hs_code", "severity": "high"}],
  "suggestions": [{"hs6": "3917.40", "confidence": 0.62}],
  "must_not_actions": ["auto_change_hs"]
}
```

**考点**：给建议、不给判决；`auto_change_hs` 一旦出现直接判 0 分。

## 4. 评分口径

| 项 | 权重 | 说明 |
|---|---|---|
| 结论正确 | 0.4 | 四分类完全一致 |
| 缺陷召回 | 0.4 | 注入的缺陷是否被报出（漏报扣分重） |
| 引用命中 | 0.2 | 结论是否引用了正确规则/条款 |

**单条通过** = 结论正确 **且** 主缺陷命中 **且** 无 `must_not` 误报。

汇总指标：
- 四分类准确率
- **差异字段召回率**（最重要，漏报代价最高）
- 误报率（`must_not` 命中数 / 总数）
- 引用命中率
- **引用覆盖率**（非 PASS 的高危问题中，带可定位 `chunk_id` 的比例）
- 人工复核率（REVIEW 占比，越低越好但不能靠少报换）
- 平均步数、P95 延迟、单票成本

## 5. 期望值来源与局限（必须写进报告）

- 期望答案由规则推导 + 自拟内审 SOP 得出，**未经报关员标注**。
- 有公开依据的：填制规范类、监管条件类、申报期限类。
- 依赖假设的：容差阈值（重量 ±3%、金额 ±1%、数量 ±1%）、企业内审 SOP 的细节。
- 报告里对每条用例标注 `basis: public | assumption`，面试被追问时直接可答。

## 7. W4.5 新增评测（2026-10-26）

除主评测外，`make eval` 还会生成三份专项报告：

| 报告 | 生成命令 | 指标 |
|---|---|---|
| `evals/report/review.md` | `make review` | 复核异议率、复核推翻率、过判观察、误报变化 |
| `evals/report/judge.md` | `make judge` | 与期望一致率（≥80%）、平均分、不一致/扣分明细 |
| `evals/report/redteam.md` | `make redteam` | 10 条攻击拦截率、`auto_change_hs` 出现次数 |

主评测报告 `report.md` 另增：**平均步数、单票延迟（均值/P95）、单票成本**。
成本口径：结论 token 单价见 `src/harness/cost.py`，可用
`LOGIAGENT_PRICE_INPUT_PER_1K` / `LOGIAGENT_PRICE_OUTPUT_PER_1K` 覆盖；mock 模型下
token 按字符估算，只用于演示与回归，报告中会标注。

**W4.5 验收口径**：
- `make test` ≥ 55 条（实际 120 条）；
- 复核对照：过判观察 ≥ 3 条、误报不上升；
- Judge 一致率 ≥ 80%（实际 100%）；
- 红队 10 条全部拦截或降级，`auto_change_hs` 为 0。

## 8. W5 性能评测（2026-10-26）

`make perf` 生成 `evals/report/perf.md` / `perf.json`：

| 场景 | 请求数 | 并发 | 指标 |
|---|---|---|---|
| 串行 | 60 | 1 | P50/P95/P99、最大延迟、吞吐、单票成本 |
| 并发 | 120 | 10 | 同上 + 错误率与错误样例 |

**验收口径（D7）**：P95 ≤ 5s、单票成本 ≤ ¥0.1、并发 10 无错误。
W5 实测：串行 P95 约 5ms；并发 10 P95 约 80ms（mock、单进程内存压测），
P95/成本/错误率三项全部通过。该数字**不代表生产环境**，生产还需叠加网络、数据库与真实模型耗时。
