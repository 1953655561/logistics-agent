# 05 · 10 分钟演示脚本

> 目标：让面试官在 10 分钟内看到“业务问题 → 架构 → 可跑系统 → 评测证据 → 取舍”。
> 默认离线 mock，断网也能跑；真实模型只是把 mock 换掉，链路不变。

## 0. 演示前 3 分钟检查

```bash
make test                 # 155 条应全绿
make eval                 # 生成 5 份报告
make gate                 # 指标门禁应全绿
# Web：任选一种
make demo                 # 无依赖兜底，最稳
make api                  # FastAPI（需要 fastapi/uvicorn）
```

确认浏览器打开 `http://127.0.0.1:8000`，能看到审核台。

## 1. 开场（0:00–1:00）

> “宁波国际物流的智慧关务已经有 AI 单证识别，解决的是‘单子读没读出来’。我做的是识别之后那一步：这张单能不能报、缺什么、该找谁补，形成可评测的闭环。”

一句话定位：**不重复造 OCR，做判断层 + 证据链 + 审批门 + 评测。**

## 2. 架构（1:00–2:30）

用 `docs/03-architecture.md` 的图讲三层：

1. **规则优先**：L1/L2/L4 确定性规则，不花 token、可解释；
2. **RAG + LLM 兜底**：L3 要素/归类冲突才检索规则库、给 6 位建议；
3. **Harness**：Loop / 工具 / 状态机 / 护栏 / 复核 / trace / 成本限流。

强调三条取舍：

- 字段比对不让 LLM 做；
- 审批门放工具层，CLI 和 Web 复用；
- 结论必须带引用（压幻觉，也让报关员敢用）。

## 3. 命令行跑一票（2:30–4:00）

```bash
python -m src.app.cli audit IMP-0019 --auto --offline
```

讲解输出：

- 结论 `FIX`，问题 `L2-13`，字段 `declaration.total_amount`；
- `evidence` 能看到发票 48000 / 报关单 47880；
- 引用 `rules#L2-13` 可回查；
- 步数、耗时、trace 路径；
- 复核意见、单票成本。

再跑一键四结论：

```bash
make demo-script
# 或 python scripts/demo.py
```

四个代表用例：`PASS / FIX / REVIEW / REJECT`，每个都能对上期望。

## 4. Web 审核台（4:00–6:30）

1. 左侧选 `IMP-0025`，点“新建审核”；
2. 右侧看问题清单、单证页签、处理轨迹、复核与护栏；
3. 找一票 `PENDING_APPROVAL`（如 `IMP-0059`），点“人工审批”：
   - 选“退回补正”，意见留空 → 提示必填；
   - 填意见后通过，状态变 `APPROVED`；
4. 点「导入单证」→「载入示例」→「导入并审核」：
   - 证明不是只能跑 60 条，任意结构化 JSON 都能审；
   - 导入后会生成新审核单并自动进入详情；
5. 切到“评测指标”：准确率、召回、误报、P95、成本、逐条结果。

讲法：

- 前端不做业务判断，只消费后端带引用的结论；
- 审批门在工具层，Web 与 CLI 同一套状态机；
- 60 条是评测集，导入是任意数据入口；没装 Node 的客户现场可用无构建兜底页。

## 5. 评测证据（6:30–8:00）

打开/展示：

| 报告 | 讲什么 |
|---|---|
| `evals/report/report.md` | 60 条准确率/召回/误报/引用覆盖，单票成本、P95 |
| `evals/report/review.md` | 单链路 vs 双链路，5 条过判观察，误报不上升 |
| `evals/report/judge.md` | LLM-as-Judge 一致率 100% |
| `evals/report/redteam.md` | 10/10 拦截，`auto_change_hs` 0 次 |
| `evals/report/perf.md` | 并发 10 P95 约 80ms，0 错误 |

一句话：**这些数字是 `make eval` 自动生成的，不是手写的。**

## 6. 成本 / 延迟 / 限流（8:00–9:00）

- 单票成本 `¥0.0002`（mock，按 token 单价折算）；
- 串行 P95 约 5ms，并发 10 P95 约 80ms；
- 限流：60 次/分钟令牌桶，超限降 REVIEW 并写 trace；
- 幂等：`case_id` 重复提交返回已有审核单，不重复计费；
- 成本/限流都可以在 `CaseService` 注入，不改业务代码。

## 7. 收尾与局限（9:00–10:00）

主动承认（别等问）：

- 没有真实客户与驻场（FDE 的 45% 是方法论，不是战绩）；
- 没有真 embedding/向量库（`RetrieverPort` 已留）；
- 没有 OAuth/多租户（只有设计说明）；
- 并发是单进程内存压测，不代表生产网络/数据库开销。

下一步：W6 已完成 Docker/CI/手册/演示；真实落地要补数据分级、权限、监控告警与客户现场试点。

## 8. 演示失败时的 Plan B

| 故障 | 处理 |
|---|---|
| Web 起不来 | `make demo`（stdlib 兜底）；仍有静态页与 `/api` |
| 前端没构建 | 直接用 `web/fallback/index.html`；`make demo` 会回退 |
| 模型不可用 | 全部命令加 `--offline`，mock 结论可复现 |
| 评测没跑 | 提前把 `evals/report/*.md` 放进仓库；用 `make eval` 现场重跑 |
| Docker 慢/没网 | 用本机 `make demo`；Dockerfile 作为交付物讲 |
