# 06 · 面试问答卡

> 用法：先背“一句话 + 三分钟”，再按岗位 JD 挑题。每题都给了可指的回文件/报告，避免空谈。
> 原则：**会的讲取舍，不会的讲边界**；不把“设计过”说成“上线过”。

---

## 0. 一句话与三分钟

### 0.1 一句话

> “我做的是 AI 单证识别之后的判断层：把一票进口单证审成 PASS/FIX/REVIEW/REJECT，每个结论都能指回规则或法规，并且能用 60 条评测和红队证明它没有乱报。”

### 0.2 三分钟结构

1. **问题**：识别只解决“读出来”，没解决“能不能报、缺什么、找谁补”；
2. **方案**：四层规则 + RAG 要素/归类 + Harness（循环/工具/状态/审批/护栏）；
3. **证据**：60 条 100% 准确率/召回、0 误报、引用覆盖 100%；复核/红队/Judge 报告；
4. **取舍**：归类只给建议、审批门在工具层、离线 mock 可复现；
5. **边界**：没有真实客户/驻场，没有真向量库，OAuth 只有设计。

## 1. 业务与定位

### Q1：为什么做这个项目？

A：目标岗位是智能体开发工程师，JD 要“单/多智能体、Harness、RAG、评测、生产化”。我不想做一个玩具聊天机器人，就选了**进口一般贸易单证审核**：业务规则清晰、有真实痛点、可评测、能体现“确定性 + LLM”的分工。完整叙事见 `docs/00-project-context.md`。

### Q2：和公司已有的 AI 单证识别什么关系？

A：**不重复造识别**。识别负责 OCR/结构化，我们消费结构化 JSON，做识别之后的判断层：四单一致、申报要素、归类建议、监管证件、审批门。面试话术：“你们已经把单子读出来了，我来判断这张单能不能报。”

### Q3：为什么不做自动申报/自动改编码？

A：边界是刻意画的：

- 自动申报要接单一窗口/海关系统，责任和合规风险不在这个项目范围；
- 归类是法律责任，D3 锁定“只给 6 位建议 + 强制人工确认”；
- Agent 只出补正建议，原始单证只读。

这不是“做不到”，是“不该由这个系统做”。

## 2. 架构与取舍

### Q4：为什么字段比对不让 LLM 做？

A：字段比对是**确定性、可解释、零 token** 的事：金额差 0.25% 就是 0.25%，不需要模型“感觉”。LLM 只用在 L3 的品名-编码冲突、规格矛盾等需要语义判断的地方，而且还要规则双判。这样更准、更便宜、更容易过审计。

### Q5：端口-适配器（六边形）怎么落地的？

A：`domain` 零依赖；`application` 只依赖端口；`adapters` 放 SQLite/LLM/FastAPI；`app` 只做组装。比如 `RetrieverPort` 现在接自研 BM25+特征哈希，换 bge-m3/Qdrant 不用动规则和循环。见 `docs/03-architecture.md`。

### Q6：审批门为什么放工具层，不放 UI？

A：CLI 和 Web 必须复用同一套状态机、审批记录和事件流。如果放 UI，CLI 就没有审批、Web 和 CLI 行为会漂。现在 `CaseService` 是唯一入口，`decide()` 同时服务审核台和命令行。

### Q7：引用链怎么防幻觉？

A：三层：

1. 规则结论自带来源（填制规范/税则/内审 SOP）；
2. 高危问题过 `rule.search` 补 `chunk_id`，可回查原文；
3. 输出校验会检查引用是否可回查，不可回查就降级。

所以 FIX/REVIEW/REJECT 都能指回规则条目或法规原文，不是模型“编一个理由”。

### Q8：多 Agent 复核到底解决什么？

A：它不是“再跑一遍模型”，而是**独立上下文**的第二意见：只看 `verdict + issues + citations`，不接触原始单证，避免被单证里的注入文字带偏。它有两类输出：

- 阻断性疑问（证据缺口、未知规则号）→ 结论升/降为 REVIEW；
- 过判观察（重复上报、仅凭关键词判禁限）→ 只标记，不改问题列表。

60 条对照里 5 条过判观察、误报 0→0；路径自检覆盖升级/降级。见 `evals/report/review.md`。

## 3. 规则与 RAG

### Q9：RAG 为什么不用真 embedding？

A：当前硬约束是零依赖、断网可跑；语料是 64 个 chunk 的规则条款，术语密集、短文本，BM25 + 特征哈希够用，评测引用覆盖 100%。真要换 bge-m3，实现 `RetrieverPort` 即可，上层不动。这是**可插拔适配点**，不是“不会”。

### Q10：检索为什么要重排？

A：实测出来的：纯 BM25 搜 `L4-41` 会召回 `L4-40`，因为分词后只是 `l4` + `41`。加“规则编号/编码精确命中”加权后第一条才对。所以纯向量/纯词频都不够，规则重排是必要的。

### Q11：归类为什么只给 6 位？

A：6 位是国际通用层级，10 位涉及本国子目和监管条件，必须人工确认。系统只给相似品名 top-3 + 6 位 + 置信度，**不自动改判**；红队还会检查 `auto_change_hs`，出现直接判 0。

### Q12：L4-41 完税价格为什么重要？

A：海关审价的核心：成交价之外，运至境内前的运费/保费、买方负担的佣金、容器包装费、特许权使用费等应计入；购货佣金、进口后费用应剔除。漏报/重复报都会导致少征/多征税。这是 W1 业务复核时补的致命缺口。

## 4. Agent / Harness

### Q13：Agent Loop 的步数预算和降级怎么做？

A：预算 8 步；单证缺失直接 REVIEW 并停；工具超时/异常重试 1 次，仍失败该步 `ok=False` 但循环继续；LLM 不可用用模板摘要兜底，不改变结论；超预算停止并保留已有结论。全部写 trace，不静默。

### Q14：工具层做了哪些防护？

A：JSON Schema 参数校验、超时、重试、统一返回；工具白名单；MCP 也只暴露 5 个工具；输入侧清洗控制字符/超长字段/注入/伪造引用；输出侧校验结论枚举、severity、引用可回查、禁用动作。

### Q15：限流和幂等怎么设计？

A：限流是令牌桶（默认 60 次/分），只拦 LLM 调用；超限 → REVIEW + trace。幂等以 `case_id` 为键，重复提交返回已有审核单，不重跑、不重复计费，并记录 `idempotent.hit` 和 `digest_matches`。批处理评测默认关限流，避免误伤。

### Q16：为什么 MCP 要单独做？

A：JD 明确要“工具/MCP”。MCP 把 5 个工具用 stdio + JSON-RPC 2.0 暴露出去，schema 直接复用 `ToolRegistry.specs()`，不写第二份；集成测试用管道输入验证 `initialize/tools/list/tools/call`。这样外部 Agent 也能接这套审核能力。

## 5. 评测、红队、Judge

### Q17：60 条评测怎么来的？期望值可信吗？

A：先写评测再写代码。期望值由规则推导 + 自拟内审 SOP 得出，**未经报关员标注**；公开依据和假设分开标注。分布：PASS 18（防误报）、不一致 16、要素归类 10、监管 8、多缺陷 8，另 15 条脏数据。局限写在 `docs/02` 第 5 节，面试被追问直接承认。

### Q18：为什么说“先写评测再写代码”是对的？

A：两个真实例子：

1. 总额容差原来写 1%，会把 120 USD 的差额判通过；评测逼着收紧到 0.1%；
2. L1-10 拿境内目的地去匹配国别表，导致全量误报；评测暴露后改成只校验启运国。

这不是审出来的，是跑出来的。

### Q19：红队测了什么？

A：10 条：指令注入（中英日俄）、伪造金额、越权改 HS、伪造引用、超大输入、重复提交、空字段、异常编码、诱导跳步、多语言混淆。全部拦截/降级，`auto_change_hs` 0 次。见 `evals/report/redteam.md`。

### Q20：LLM-as-Judge 怎么避免自嗨？

A：Judge 是独立 rubric：结论 50% + 召回 35% + 引用 15%，PASS 误报扣分；与 60 条 expected 比对，出不一致清单和扣分明细。默认确定性 rubric（零 token、可复现），接真模型可切 LLM 打分，失败回退并标 `degraded`。一致率 100% 不是“Judge 说好”，是“和期望一致”。

## 6. 生产化与交付

### Q21：成本和延迟怎么测？

A：`AuditLoop` 记录每次 LLM 的 usage，`CostMeter` 按可配置单价折算；`evals/perf.py` 跑串行 60 + 并发 10 的 120 次，出 P50/P95/P99、吞吐、单票成本、错误率。mock 下并发 P95 约 80ms、单票 ¥0.0002；生产要叠加网络/DB/真实模型耗时。

### Q22：Docker/CI 怎么做的？

A：Docker 多阶段：node 构建 AntD → python:3.12-slim 运行时，非 root、healthcheck、compose 挂 `var`。CI 三条：Python 测试+评测+指标门禁、AntD 类型生成+构建、Docker 构建。门禁 `scripts/gate.py` 卡准确率/召回/误报/引用/成本/P95/红队，不达标直接 fail。

### Q23：客户现场没网、没 Node 怎么办？

A：两条兜底：

1. `make demo` 用 stdlib `http.server`，不依赖 fastapi/Node；有 `web/dist` 就服务 AntD，没有就服务 `web/fallback/index.html`；
2. 全部模型调用可 `--offline` 走 mock，结论可复现。

这是 FDE 场景的“先能演示，再谈接入”。

### Q24：你在这个项目里最像 FDE 的部分？

A：我做了《报关员使用手册》、反馈闭环（分类/时限/周复盘/指标）、10 分钟演示脚本和兜底方案；也主动写清“没有真实客户/驻场”。这是 FDE 的方法论，不是战绩。见 `docs/04`、`docs/05`。

## 7. 反思与边界

### Q24.1：页面里 60 个选项是不是写死的？能审自己的数据吗？

A：60 条是**评测集**，不是产品输入边界。审核台有「导入单证」，支持粘贴/上传任意结构化 JSON；
API 的 `POST /api/cases/import` 和 CLI 的 `--docs` 也都能接任意单证。我现场用 `CUSTOM-DEMO-1/2`
演示过：不在 60 条里，正常单 PASS；改总价和毛重后变成 FIX，报 `L2-13` / `L2-15`。
60 条固定是为了回归可复现；生产里数据来自上游 OCR/识别，不是让人手工贴。

### Q25：项目最大的坑？

A：三个：

1. **运保费规则写反**：进口 FOB/CFR 买方支付的运保费应计入完税价格，原稿写成“不得申报”；业务复核才发现；
2. **改编码要四单同步**：只改报关单会造成 L2-11 假阳性，生成器也要遵守四单一致；
3. **SQLite 跨线程**：FastAPI 线程池里直接报 `SQLite objects created in a thread...`，W5 加 `check_same_thread=False` + 锁才解决。

共同点：**问题都是跑出来的，不是想出来的。**

### Q26：如果重做会改什么？

A：三件事：

1. 更早接真实报关员做标注，别让期望值全靠自拟 SOP；
2. 把评测集版本化和反馈闭环做成产品，而不是文档；
3. 更早做并发/幂等/权限，这些都是上线才暴露的。

### Q27：你不会什么？

A：不装会：

- 没有真实客户/驻场，FDE 的采用率、任务成功率没有真实数据；
- 没有真 embedding/向量库，RAG 是轻量实现；
- 没有 OAuth/多租户实现，只有设计说明；
- 没做 GraphRAG、多模态、A2A，但知道它们解决什么问题。

## 9. JD 覆盖对照（30 秒版）

| JD 要求 | 我的证据 |
|---|---|
| 单/多智能体、Harness | Loop + 工具 + 状态机 + 审批 + 护栏 + 复核 + MCP |
| RAG 全链路 | BM25+特征哈希混合、重排、引用回查、64 chunk |
| 评测驱动 | 60 条评测、复核对照、Judge、红队、性能门禁 |
| 生产化 | Docker 多阶段、CI、trace、成本/限流/幂等 |
| FDE | 使用手册、反馈闭环、演示脚本、兜底方案（无真实客户） |
| Python/工程 | 155 条测试、零依赖核心、端口-适配器 |

> 覆盖度约 90%，剩下 10% 主动承认：真实客户/驻场、真向量库、OAuth/多租户、GraphRAG/多模态。
