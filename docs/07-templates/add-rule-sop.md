# 新增一条审核规则的标准动作（add-rule SOP）

> 适用：`src/rules/**` 里的确定性规则（L1 / L2 / L3 / L4）。
> 目标：新增规则可判定、可引用、可回归、可验收，且**不破坏已有 60 条评测**。
> 现行规则库 46 条（L1 10 / L2 14 / L3 10 / L4 12），以 `docs/01-rule-library.md` 为准。

## 0. 先判断「该不该新增」

- [ ] 用 `rule.search` 或直接读 `docs/01` 搜一遍：已有规则是否只是容差 / 字段不同？
      只是参数不同 → **参数化现有规则**，不新增编号。
- [ ] 缺陷是否已被别的规则覆盖？重复上报会抬高问题数、污染复核的“过判观察”。
- [ ] 字段是否存在、是否可判？自由文本、缺失字段、需要外部舱单/税则库才能判的，
      先记为“不覆盖”，不要写一个永远 `PASS` 的假规则。
- [ ] 判定是否必须由人做？必须人工判断的，结论给 `REVIEW`，不要给 `FIX` 假装能自动改。

## 1. 编号与分层

- 现有编号段：`L1-01..10`、`L2-11..24`、`L3-23..32`、`L4-33..44`。
- 新编号**顺延且不复用**；编号一旦进入文档与引用链（`rules#Lx-yy`）就视为稳定契约。
- 分层规则：
  - L1 完整性与格式（表头、日期、币制、单位、项数、齐套、金额勾稽、重量、件数、格式）；
  - L2 单证一致性（品名、数量、金额、币制、重量、件数、收发货人、成交方式、原产国、
    单号、唛头、要素跨单）；
  - L3 申报要素与归类（要素齐全、枚举、材质、用途、工艺、成分、单位换算、归类建议）；
  - L4 监管与合规（证件、协定税率、贸易方式、禁限、双反、食品、标签、舱单、完税价格、
    期限、木质包装、许可证有效期）。
- 实现文件：`src/rules/l1_format.py` / `l2_consistency.py` / `l3_elements.py` /
  `l4_compliance.py`；用 `@rule("Lx-yy", L, "标题", "来源")` 注册。

## 2. 判定逻辑

- [ ] 明确输入字段与取值路径（例：`declaration.total_amount`），写进规则注释。
- [ ] 容差集中放在 `src/common.py`，不在规则里散落魔法数；写清为什么是这个容差
      （例：行级 1%、总额 0.1%、散装 3%）。
- [ ] 归一化：公司名忽略 `LTD/LIMITED/PTE` 等法律形式词；品名去规格、统一中英；
      数字字符串转数值要容错。
- [ ] 双方都有值才比对（参考 L2-24），缺失留给专门的完整性规则，避免同一缺陷报两次。
- [ ] **脏数据不能静默跳过**：有值但解析失败（日期、金额、单位）必须报出来，
      参考 L1-02 / L4-42 的修复；`try/except` 后 `return PASS` 是禁止写法。
- [ ] 边界用例想清楚：空列表、0、单商品项、多商品项、散装、跨币制、四单缺一。
- [ ] 规则不得修改入参 `ctx`（只读），不得调用网络 / LLM（L3-25/26/29 的模型调用是
      既有特例，新规则默认纯确定性）。
- [ ] 单条规则抛异常会由 `src/registry.py` 降级为 `REVIEW` 并带 `error`；不要依赖它
      掩盖逻辑错误。

## 3. 结论口径

| 结论 | 什么时候用 | 反例 |
|---|---|---|
| `FIX` | 有明确、可自动给出修正建议的问题 | 需要专业判断的归类争议 |
| `REVIEW` | 规则冲突、需人工判断、可补办的证件 | 把濒危物种也降成 `REVIEW` |
| `REJECT` | 依规不得申报：禁限类、缺前置资质 | 把可补办的许可证缺失判 `REJECT` |
| 不改结论 | 纯建议类（L3-29 归类建议） | 用建议去改判 HS |

- 多规则冲突取最严重（`PASS < FIX < REVIEW < REJECT`），并在说明里注明冲突。
- 归类只给 6 位建议 + 人工确认，**禁止** `auto_change_hs` / `change_hs` /
  `auto_reclassify` 这类禁用动作。

## 4. 来源与引用

- [ ] `source` 写可回查的短来源（如“审价办法”“内审 SOP”“税则”）。
- [ ] 在 `docs/01-rule-library.md` 对应分层表格中新增**一行**，列齐：
      编号 | 规则 | 判定逻辑 | 违反结论 | 来源。
      **这不是可选项**：`src/rag/corpus.py` 按行解析 `docs/01` 生成
      `rules#Lx-yy` 语料，行不写，`rule.search` 就检索不到，引用链会断。
- [ ] 引用要求：任何 `FIX` / `REVIEW` / `REJECT` 都必须能指回规则条目或法规原文；
      输出里的 `citation_chunk` 必须是真实 `chunk_id`，不得编造（伪造 `rules#L9-99`
      会被护栏识别并降级）。
- [ ] 若来源文本有歧义，把假设写进变更记录（D4：报告里标注“假设”）。

## 5. 实现骨架

```python
"""Lx 规则：一句话说明这条规则管什么、不管什么。"""
from __future__ import annotations

from ..common import get, num
from ..issue import Issue, RuleResult
from ..registry import rule

L = "L2"  # 本层


@rule("L2-25", L, "标题", "来源")
def check_xxx(ctx):
    issues = []
    # 1) 取字段；缺失时按约定跳过或报 REVIEW，不默认 PASS
    # 2) 归一化 / 容差比较；差多少、哪一侧更大写进 evidence
    # 3) 每条问题定位到 field_path，给 suggestion（只建议，不代替人改单）
    return RuleResult("L2-25", L, "标题", "FIX" if issues else "PASS",
                      issues, "来源")
```

- `Issue` 必填：`rule_id` / `field_path` / `severity`（high|mid|low）/
  `message` / `evidence` / `suggestion`。
- 不截断问题清单（历史教训：`rules.audit` 曾硬编码 `issues[:20]`，线上少报 9 条）。

## 9. 门禁与基线（收尾必跑）

```bash
python -m unittest discover -s tests       # 单测全绿，条数不低于基线
python scripts/baseline_check.py           # 应显示 ✅ 未发现退化
make eval                                  # 主评测 + 复核 + Judge + 红队 + 性能
make gate                                  # 指标门禁（当前 11 项）
```

- `scripts/baseline_lib.py` 的比较口径：
  - 准确率 / 召回 / 引用覆盖**下降**算退化；误报率**上升**算退化；
  - 手改单问题数**下降**算漏报；
  - 干净样例的规则集合变化会被拦（要么是误报，要么是口径变化，必须解释）；
  - 测试数下降算退化，测试失败直接失败。
- 新增规则通常会**增加**问题数，不会触发“问题数下降”；若干净样例新增命中，
  先确认是不是误报，不要急着 `make baseline`。
- 只有确认变化是预期的，才允许刷新基线（`make baseline`），并在提交说明里写原因。
- 注意：早期文档写 `make gate` 9 项，当前 `scripts/gate.py` 是 **11 项**
  （新增无引用断言率、引用不可回查率），以脚本为准。

## 11. 常见坑（都真实踩过）

1. 规则写了没实现，或在脏数据上 `except: return PASS` → 单点注入才发现漏报。
2. 只改报关单不改四单同步，导致 L2-11 假阳性（改编码要四单一起改）。
3. 文档里加粗的行导致 RAG 漏切（`**L4-41**` 曾整块没进索引），改 `docs/01` 后
   用 `rule.search` 回查一次。
4. 在 `rules.audit` 里截断问题清单，评测走 `engine.audit` 看不出来，线上少报。
5. 同一缺陷被两条规则各报一次，复核的“过判观察”被噪声拉高。
